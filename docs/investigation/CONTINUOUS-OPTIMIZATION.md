## Candidate inventory and priority

Evaluate each category, but do not implement each by default. Rank by measured impact, reproducibility, correctness risk, user value, complexity, budget and expected cost. Include evidence against each hypothesis and stop investigating a candidate when the next test has low expected value.

1. **HTTP path:** reproduce the reported cache-hit delay, isolate each gateway/worker connection, test TCP_NODELAY and keep-alive behavior separately, measure connection churn and CPU, and compare both hit and miss workloads. Respect server/client compatibility; add a regression check for behavior without brittle wall-clock thresholds.
2. **Runtime and compute:** CPU affinity and container quota versus `hardware_concurrency`, ORT thread count and execution modes, session options and graph optimization. Test that override parsing and capacity fallback are safe, and compare results across CPU limits rather than assuming two vCPUs generalize.
3. **Batching and queueing:** deadlines, maximum batch size, saturation, fairness, backpressure and shutdown. Measure throughput/latency tradeoffs over cache misses at multiple concurrency levels; inspect promise completion and exception paths. Do not equate maximum throughput with acceptable latency.
4. **Memory and serialization:** measure copies, padded input tensor construction, allocation, JSON parsing and output serialization; investigate input shape validation and output bounds first. Keep numerical equivalence, model constraints and API compatibility explicit.
5. **Cache and routing:** hit/miss rates, duplicate in-flight requests, eviction, cache key correctness, concurrency and worker routing. Measure mixed and unique workloads; do not optimize only an artificial 100% hit case.
6. **Gateway and service reliability:** connection pooling, synchronization, logging, timeouts, retries, circuit-breaker behavior and failure recovery. Fault-inject on loopback only; verify no duplicate unsafe action, request mismatch or hidden error. Prioritize demonstrated defects over marginal speed gains.
7. **Measurement quality:** warm-up, client CPU contention, sample counts, randomization, independently timed batch samples, host load, model checksum, and closed-loop bias. Consider a bounded open-loop test only if needed and safely implemented. Do not mislabel percentiles or infer per-request compute from whole-batch timings.
8. **Scaling and larger design changes:** document potential multi-worker or multi-host experiments and network/security/cost implications. A single-host result cannot establish distributed scaling. Do not deploy a public service, add paid services, redesign architecture, use GPUs or perform multi-host cloud experiments without specific applicable approval.

## Repeatable optimization cycle

1. Select the highest-value untested hypothesis and define exact baseline, intended one-variable change, alternatives, expected failure modes, correctness tests, measurement, success and regression criteria **before** implementing. If only tuning a configuration, record the effective configuration for every run.
2. Implement the smallest maintainable change and tests. Preserve API and output behavior unless an authorized change explicitly requires otherwise. Test edge cases, failure paths and numerical tolerance as relevant. Review actual diff and reject unnecessary abstraction and unrelated modifications.
3. Run matched local baseline and changed builds using identical model, dependency versions, input workloads, concurrency, timing instrumentation and resource limits. Repeat and alternate order where practical; record raw samples, p50/p95, throughput, failures, CPU/memory, and run-to-run variability. Include hit, miss and mixed workloads as relevant. Do not infer robust p99 from a tiny sample. Never compare results across different code, environments or workloads without labeling confounders.
4. Where safe and permitted, validate the most promising candidates on temporary AWS resources under the existing project budget. Inspect preflight, current pricing, actual available cost data and cleanup status before each run. Estimate maximum cost and leave contingency; after each run preserve logs, verify resource deletion and update ledger. If cleanup or costs are uncertain, stop further cloud work and follow recovery instructions. Do not sacrifice cleanup to continue an experiment.
5. Analyze results honestly, including regressions, noise, correctness and tradeoffs. Retain the improvement only if it is justified; do not revert or delete pre-existing user work. If a newly created change is undesirable, explain it and use a non-destructive, authorized way to resolve it. Keep evidence for rejected candidates.
6. Update the experiment ledger and select the next candidate. Continue across turns while candidates meet the decision criteria. Do not loop indefinitely on repeated errors, run unbounded workloads, make progressively riskier changes to create a resume metric, or run arbitrary cloud instances overnight.
